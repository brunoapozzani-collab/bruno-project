# THE WALL — unnamed-project

Nine rules. They are enforced by hooks, not merely written here. A rule that
only exists in prose is a suggestion; every rule below has something that
refuses.

## 1. Every job starts with a "Requires:" block

Before the first tool call of any job, list what the job needs and whether each
item is present:

```
Requires:
- Deployed app reachable (none)     — present / MISSING
- Verification command runnable                — present / MISSING
- Screen or surface being changed              — present / MISSING
- Credentials / libraries the job needs        — present / MISSING
```

If **anything** is MISSING, stop and report it. Do not improvise a workaround,
do not substitute a different screen, do not verify an internal value because
the real one would not load. A missing requirement is a report, not a puzzle.

## 2. DONE means proven on the running application

A job is done when the app running from this branch (this project has no deploy URL — record how it was run) has been exercised and the result **read
back and described in words**.

- Capture the real surface — desktop (1440×900) and mobile (375×812) for
  anything a person looks at.
- **Read the artefact back** and describe what actually happened. An assertion
  with no read-back is not evidence.
- Verify the **actual thing you changed**, never a different, easier one.
- **Never verify on an internal value instead of the rendered result.** A query
  that says the data is correct proves nothing about what the user sees.
- **Correct data behind a broken or confusing screen is not done.**
- Before/after for every visual change.
- If capture fails, say so plainly. Never silently skip.

## 3. Slow is broken

Any surface taking longer than about **2 seconds** to become usable is a
**defect**, not a note. Fix it or report it as a defect. Do not mention it in
passing and move on.

## 4. The usability bar

If someone who has never seen it cannot work out **what it is for** and **what
to do next**, it is not finished. This is blocking, equal in weight to
correctness. Technically right and practically unusable fails.

## 5. What exists is what they need

Before adding **any** new panel, card, badge, button, screen, table or command,
check whether an existing one already serves that purpose and **extend it**.

> "They don't need new screens, they need the existing ones FIXED."

## 6. DANGER LIST — stop and ask the owner

Do not proceed on any of these. Stop, report, wait:

| # | Danger |
|---|--------|
| 1 | **Any database migration** — schema change of any kind, in any dialect |
| 2 | **Any write to production data** (INSERT / UPDATE / DELETE against prod) |
| 3 | **Anything touching money** — prices, costs, margins, invoices, payments |
| 4 | **Anything touching stock quantities or write-offs** |
| 5 | **Anything sent to a third party** — email, WhatsApp, webhooks, external APIs |
| 6 | **Anything irreversible** — deletions, overwrites, deploys, anything with no restore path |

Production data access from an agent session is **read-only**.

## 7. Never run destructive git commands. Never print secrets.

- **Banned, always:** `git reset --hard`, `git clean -fd`, force-push in any
  form, `git branch -D`, `git tag -d`, `git rebase`, `git checkout .`,
  `git filter-branch`, `git update-ref -d`, reflog expiry. If you believe one is
  needed: **stop and report instead.**
- **Never push directly to `main`.** Work on a branch, open a PR.
- **Never** print an env file, a connection string, a password or an API key
  into output, a log, a commit message or a command line. Load secrets
  in-process; never `echo` them and never pass them as a visible argument.

## 8. No routing around a guard

If a hook or guard blocks a command, do **not** find another way through — no
`--force`, no encoding, no aliasing, no temporary allow-file. Stop and report.
